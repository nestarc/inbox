# 로컬 MVP 성능 기준값

실행일: 2026년 10월 27일 22시 30분 KST. 이 결과는 재현 가능한 소규모 로컬 기준값이며 서비스 처리 용량이나 SLA가 아니다.

## 환경

- Node 24.11.1, Prisma 7.10.1, PostgreSQL 16.15
- macOS arm64, Apple M1 Pro, 논리 CPU 10개
- Docker `postgres:16-alpine`, 임시 tmpfs 데이터, loopback 연결
- payload 265바이트, Prisma pool 최대 12개와 관리 연결 2개
- 수신 동시성 8, worker 동시성 4, 시나리오당 수신 요청 500회

## 결과

| 시나리오                    | 수신 요청/초 | 수신 p50 | 수신 p95 | 수신 p99 | worker 처리 소요 | 새 기록 / 중복 |
| --------------------------- | -----------: | -------: | -------: | -------: | ---------------: | -------------: |
| 새 테이블                   |    2,197.939 | 3.338 ms | 5.390 ms | 8.086 ms |       813.740 ms |        500 / 0 |
| 완료 기록 1만 개 보존       |    2,735.363 | 2.742 ms | 4.440 ms | 6.553 ms |       774.389 ms |        500 / 0 |
| 완료 기록 1만 개와 중복 90% |    2,242.860 | 3.420 ms | 4.930 ms | 5.971 ms |        76.884 ms |       50 / 450 |

모든 시나리오에서 수신과 worker 오류는 0건이었다. 같은 transaction에서 기록한 업무 효과 수는 각각 500개, 500개, 50개로 확인했다. 표의 요청/초는 수신 단계의 처리량이며 handler의 지속 처리량과 다르다.

## 재현과 해석

```sh
npm run benchmark
```

[benchmark.mjs](../../scripts/benchmark.mjs)는 테스트 실행기가 만든 임시 DB만 허용하며, 환경·지연 백분위·처리량·업무 효과 수·오류를 JSON으로 출력한다. 기존 애플리케이션 DB에는 실행하지 않는다.

세 시나리오는 고정 순서로 한 번 실행했다. 뒤 시나리오의 JIT·cache 예열이 더 높은 수신 처리량의 원인일 수 있으므로 완료 기록이 많을수록 빨라진다는 결론을 내리지 않는다. tmpfs, 작은 payload, 짧은 handler, 동일 호스트 연결은 운영 환경과 다르다. 큰 payload, 디스크 I/O, 장시간 backlog, DB pool 포화, tenant별 공정성, 반복 표본과 분산 측정은 별도 부하 시험이 필요하다.
